# 2.1 Chunk encodings against Parquet

Roadmap item 2.1: size and scan speed of candidate encodings for compacted per-series chunks
(`docs/spec.md` §7, `docs/format.md` Part B), on synthetic per-second data, against the Parquet reader. The code
is the spike crate `spikes/encodings`; it is not part of the engine.

```sh
cargo run --release -p encodings -- --reps 7   # about 90 s; prints the tables below
cargo test -p encodings                        # round-trip and property tests (run in CI, one job on Linux)
```

## Data
A deterministic generator simulates the log of a store whose series all report once per second. Within each
second the readings of all series arrive in a random order and take consecutive positions, so a series' position
steps by about the number of series, with noise. Each UTC day is then compacted per series into a chunk of current
facts (for each `t`, the fact with the highest position) and, where there are any, a chunk of revisions.

| Shape | Values | Other features |
|---|---|---|
| temperature | daily sine, slow random walk and noise; 0.01 resolution | device-stamped, exact 1 s grid |
| energy counter | kWh, rising by a varying load; 0.001 resolution | device-stamped |
| boolean | state 0/1, mean dwell 10 minutes | device-stamped |
| gappy gauge | random walk and noise; 0.1 resolution | host-stamped at nanosecond resolution with 0–8 ms jitter; outages of 1–30 minutes (about one an hour); 0.1 % bad readings without a value; runs of suspect quality; `host_time` flag |
| dense with revisions | integer-valued; 1.0 resolution | 0.1 % of seconds corrected 5 s to 15 min later (later position; `late` beyond 5 minutes) |
| °F→°C | the temperature shape read in °F at 0.1 resolution and converted to °C: almost no value is decimal | device-stamped |
| 0.1 % computed | the temperature shape, with about 0.1 % of values replaced by the mean of the last three readings (not decimal) | device-stamped |

Values are quantised by dividing an integer by a power of ten, which gives the same `f64` as parsing the decimal
text a device sends. No value is NaN or infinite; a bad reading has no value (value bits 0, as in format A.5).

## Candidates
Every candidate stores, per chunk, the columns `t` (i64 nanoseconds), value (f64 bits, i64 or state index),
quality (u8), flags (u16) and position (the u64 sequence; the generation is constant per chunk). The value column
holds nothing for a row without a value: the own encodings rely on the `no_value` flag, Parquet on a null. Rows are
grouped in blocks (own) or data pages (Parquet) of 4,096, so a range scan decodes only the blocks it overlaps.
Every candidate that compresses uses zstd 1.5.7 at level 3. One file holds all chunks of a day: own encodings with
a 24-byte directory entry per chunk; Parquet with one row group per chunk.

| Candidate | `t`, position, i64 value | f64 value | quality, flags, state |
|---|---|---|---|
| (a) plain + zstd | little-endian, zstd | little-endian, zstd | little-endian, zstd |
| (b) dod/XOR/RLE | delta-of-delta, Gorilla-style bucketed bit codes (i64 value: as delta below) | Gorilla-style XOR | run-length (LEB128) |
| (b) delta/XOR/RLE | delta, frame-of-reference bit-packed per 128 | Gorilla-style XOR | run-length |
| (b) delta/XOR/RLE + zstd | as above, then zstd per column per block | | |
| (d) delta/decimal/RLE | delta, bit-packed per 128 | scaled decimal (below) | run-length |
| (d) delta/decimal/RLE + zstd | as above, then zstd per column per block | | |
| (c) Parquet, BYTE_STREAM_SPLIT | DELTA_BINARY_PACKED | BYTE_STREAM_SPLIT | dictionary (RLE_DICTIONARY) |
| (c) Parquet, ALP | DELTA_BINARY_PACKED | ALP | dictionary |
| (c) Parquet, dictionary | DELTA_BINARY_PACKED | dictionary (plain once the dictionary passes 1 MiB) | dictionary |

**Scaled decimal**, per block, after ALP but simpler: the candidate exponents are the smallest `e` for which each
of 32 sampled values is exactly `n / 10^e`; the block takes the `e` with the lowest estimated size, counting
3.32 × `e` bits per fitting value and 80 bits per value that does not fit (an exception). The `n` are delta-coded
and bit-packed per 128; each exception is stored as its index and its 64 bits. If no sampled value is decimal, or
exceptions make the block larger than XOR, the block is XOR-coded, and that XOR stream is compressed with zstd
when this makes it smaller.

Candidate (d) and the ALP and dictionary variants of (c) were added to the three planned candidates (a)–(c):
`docs/design.md` names a decimal encoding and states its size budget against Parquet with ALP, and a dictionary
suits values drawn from few distinct readings. Parquet is written and read with
the `parquet` crate 60.1 (Arrow writer and reader, data page v2). Page statistics, and so a column index, are
written for `t` only, matching the own format's first and last `t` per block; offset indexes are written for every
column, so that a row selection skips pages. Value columns are
written only for kinds present in a file: `value` (DOUBLE), `state` (INT32, dictionary) and `integer` (INT64,
DELTA_BINARY_PACKED), each null in rows of other kinds. Every file measured is checked for the encodings in the
table and for pages of 4,096 rows in every column.

Every candidate is checked to round-trip every chunk bit-exactly, in full and for the range scanned. The tests
(`cargo test -p encodings`) also round-trip hand-built edge cases through all nine candidates: −0.0, subnormals,
values near `f64::MAX`, non-decimal values (through BYTE_STREAM_SPLIT and ALP too), every quality, flag bits 0–5,
state indexes up to `u16::MAX`, `i64::MIN` and `i64::MAX`, positions above `i64::MAX` (to `u64::MAX`), a block in
which no row has a value, exceptions and the XOR fallback inside the container, repeated `t`. A property test
does the same for arbitrary chunks of each kind (up to two blocks long, with any finite value bits).

## Method
Release build, one thread, everything in memory. For each day, every candidate encodes all chunks of the day as one
file; this is repeated 7 times, the candidates taking turns within each repetition in an order rotated by one each
time. Every file is then checked, untimed. Then, again taking turns, each candidate opens the file (Parquet: parses
the footer and page index), decodes every chunk in full and range-scans every current chunk for one hour
(12:00–13:00), 7 times. The times of each repetition are summed over days; the tables give the median repetition
and, in brackets, the lowest and highest values. Decoding produces column vectors (for Parquet: Arrow arrays copied into
them). A chunk is decoded right after it was encoded, so the data are in memory and mostly in cache; this measures
the decoders, not storage. Apart from "file open", the Parquet reader uses a footer and page index parsed once per
file, outside every timed step. A range scan in Parquet uses the page index of `t` to select whole pages and a row
selection to read them, as a query engine does.

Machine: a laptop-class 12-core ARM64 CPU (one core used); Rust 1.100. Builds and tests ran at lowered priority;
the measurement itself ran at normal priority, so that the scheduler places it like any foreground work and every
candidate gets the same kind of core. The data are deterministic, so sizes do not vary between runs.

## Findings
- **Values decide the size, and the value type decides the margin.** With decimal readings stored as `f64`, the
  scaled-decimal column takes 0.35 bytes per row, against 0.56–0.58 for Parquet's ALP, 0.76–0.78 for a Parquet
  dictionary, 1.3 for BYTE_STREAM_SPLIT with zstd and 2.2 for XOR. ALP loses most on the counter (0.75–0.79
  against 0.14 bytes per row for the value), whose values span a wide range within a vector and need deltas.
- **As `i64` with a decimal scale, Parquet draws level.** For the temperature, counter and revised shapes the own
  delta coding takes 0.46, 0.14 and 0.76 bytes per row for the value; Parquet's DELTA_BINARY_PACKED with zstd
  takes 0.44, 0.08 and 0.77. The own `i64` sizes equal its `f64` scaled-decimal sizes (the same integers are
  stored). Over that data set the columns take 1.57 bytes per row in the own encoding and 1.56 in Parquet; the
  totals, 1.58 against 1.60, differ only by Parquet's footer and page-index cost (overhead 0.01 against 0.03 bytes
  per row, visible on its own in the boolean shape).
- **Values that are not decimal need per-value exceptions.** With about 0.1 % computed values almost every block
  holds one, so a whole-block fallback turns 0.47 bytes per row into about 4.6 (the XOR column above). With
  exceptions the own encoding takes 0.92 bytes per row against 1.06 for Parquet with ALP and 1.27 with a
  dictionary. For converted values (°F→°C), almost none decimal, the XOR fallback alone takes 1.84 bytes per row;
  compressing the fallback with zstd brings it to 0.87, against 1.03 for ALP, but a Parquet dictionary takes
  0.71: the converted values come from few distinct readings. Both non-decimal shapes have low entropy; values
  with full 17-digit mantissas would compress far less in every candidate. The exception search slows the own
  encoder to under 90 million rows per second on such data.
- **Delta with bit-packing beats Gorilla-style delta-of-delta** for `t` (0.56 against 0.88 bytes per row) and
  position (1.05 against 1.27 with 100 series), and decodes 1.5–2 times as fast. Bucketed codes spend a bit per row
  even on a perfect grid and many bits on jitter; a frame of reference per 128 values costs almost nothing on a
  grid and fits jitter to its width. The host-stamped gauge's jitter makes `t` its largest column.
- **zstd adds little after the specialised encodings** (1.98 to 1.94 bytes per row) and costs about 30 % of
  encode speed and 10–20 % of decode speed; it pays only on the XOR fallback.
- **Position is the second-largest column**: 0.4–0.7 bytes per row with 4–10 series, 1.05 with 100, because
  arrival order within a second varies. It grows with the number of series reporting together.
- **`received_at` stored per fact would cost about 4 bytes per row** (6.6 with plain + zstd), more than the five
  other columns together; the generator gives every fact its own arrival time, and the totals exclude it. In the
  log it is a per-batch field (format A.5), so a compacted segment could instead keep a per-batch table (first
  sequence, `received_at`) shared by all its series and find a fact's `received_at` from its position. That is
  cheap when batches hold many readings (an adapter that delivers a whole poll at once) and no cheaper than the
  column when each batch holds one. Part B has to choose; spec §7 requires only that it is kept.
- **Speed.** The own decoder runs at 270–400 million rows per second and range-scans an hour of one chunk in
  25–34 µs; Parquet decodes at 137–250 million rows per second and takes 34–59 µs with BYTE_STREAM_SPLIT or ALP
  (77–82 µs with a dictionary on decimal data), with the footer cached. A 1-hour drill-down over 100 series is
  therefore about 6 ms in Parquet, and a whole day of one series under 1 ms, inside the 50 ms chart budget.
  Parsing a footer and page index takes about 0.23 ms for 120 row groups, so a reader must cache them. In-memory
  decoding is not the bottleneck on this machine for either format; I/O, a cold cache and the target hardware are
  left to roadmap item 10.1.

## Conclusion
If compacted data are stored in the own format, carry into `docs/format.md` Part B: `t`, position and `i64` values
as deltas, frame-of-reference bit-packed per 128; `f64` values as scaled decimals with per-value exceptions,
falling back per block to XOR, zstd-compressed where that is smaller; run-length for quality, flags and state;
blocks of 4,096 rows behind a directory of first and last `t`; no general-purpose compression elsewhere. A
dictionary for `f64` blocks with few distinct values is worth a further look (the °F→°C shape).

This departs from `docs/design.md` ("Segment format") in two places, which gate 2.3 should update there and in
Part B together:
- **timestamps:** delta with frame-of-reference bit-packing, not delta-of-delta;
- **decimal values:** a simplified ALP (one exponent per block, no second factor, exceptions stored raw) whose
  fallback is XOR plus zstd, not ALP with a plain XOR fallback.

On size, the own encoding is 8–14 % smaller than Parquet with ALP when decimal readings are stored as `f64`, and
1 % smaller when the decimal series are declared `i64` with a scale, a difference that is only Parquet's footer
and page index. On the two non-decimal shapes it is 13 % smaller than the best Parquet variant on one (computed
values, against ALP) and 23 % larger on the other (converted values, against a dictionary). So whether the format
"clearly beats Parquet" (`docs/design.md`) depends mainly on how series are declared: if adapters declare decimal
sources as scaled `i64`, the measured margin is negligible. That is for gate 2.3 to weigh; this measurement does
not settle it. Decoding speed does not decide gate 10.2 on this evidence (see Speed above).

Limits: synthetic data; in memory and in cache; one thread; Parquet's ALP support is recent, and other readers may
not yet read it; the non-decimal results rest on two low-entropy shapes. The generator reshuffles the arrival
order within every second and gives every fact its own arrival time; the position and `received_at` costs, and the
gap between the 10- and 100-series data sets, follow from that. Devices that report in a stable order would shrink
position in every candidate and widen the margin against Parquet.
