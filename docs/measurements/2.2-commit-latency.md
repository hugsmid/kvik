# 2.2 Commit and sync latency, group commit, sync failure and a full disk

Roadmap item 2.2. The code is the spike crate [`spikes/commit`](../../spikes/commit), which is not part of the
engine. Only macOS was measured; Linux and Windows were not (see Method).

## Summary

- **Durable call per OS.** macOS: `fcntl(F_FULLFSYNC)`. Linux: `fdatasync` on a zero-filled preallocated
  segment, and `fsync` where the length or a directory entry changes. Windows: `FlushFileBuffers`. On macOS a plain
  `fsync` is about 300 times cheaper (0.01 ms against about 4 ms), but its manual page says that it is not durable.
- **Latency with the durable call.** Measured on macOS, window 0, 100 series, at 100 to 100,000 readings/s. The
  figures are medians of three runs:
  - delivery to an in-process consumer takes 3.9–5.8 ms at p50, 4.9–13.5 ms at p99 and 8.9–20.4 ms at p99.9;
  - `design.md` sets the budget for Linux with an NVMe SSD (p50 ≤ 5 ms, p99 ≤ 20 ms) and does not hold macOS to
    it. Against those figures, p99 passes in every window-0 cell. p50 passes only at 100 and 100,000 readings/s;
    at 1,000 and 10,000 readings/s it was above 5 ms in every run (medians 5.71 and 5.81 ms);
  - the stretch goal of p50 ≤ 2 ms is out of reach with this sync, which alone takes about 4 ms;
  - p99 is not reliably under 10 ms on this machine. The worst window-0 cell was 13.5 ms, at 10,000 readings/s:
    all three runs there were high (13.0–14.7 ms) while other work held the CPUs (the generator was held up for up
    to 10 ms). A previous run gave 9.0 ms.
- **Group commit.** Window 0 is enough. While a sync is in flight the next batch fills by itself: from one reading
  per batch at 100/s to about 330 per batch at 100,000/s. From 1,000/s up, the rate settles at 250–310 syncs/s.
  A window adds about its own length to latency. Its only gain is fewer syncs. The ceiling is 7.2 million
  readings/s with 1 MiB batches.
- **Mark sync.** Syncing the mark once a second, on the writer thread or on its own thread, stayed within the
  run-to-run spread of not syncing it at all. On its own thread the mark sync itself took about 9 ms against about
  4 ms (the ranges do not overlap), because it waits on the log's sync. Syncing the mark after every batch, the rule for a platform without a boot
  identifier, halves the commit rate and doubles latency.
- **Write amplification.** In log bytes it is 9.3× the payload for one reading per batch, falling to 1.0× for
  large batches. The host wrote about 85–100 KiB to the device per `F_FULLFSYNC` on APFS, which makes the sync rate,
  not the data, what sets the host writes. At 100 unbatched 1 Hz series that is about 0.75 TB of host writes a day.
- **Failures.** A sync error makes the writer read-only, with exactly one sync call and no acknowledgement. Below
  the critical mark the writer stops taking from the queue, so emits wait and the wait is measured. `ENOSPC` is
  seen at segment creation, at a write or at a sync, depending on the file system. Two questions were recorded:
  Q-86 (`ENOSPC` when a segment is created) and Q-87 (a mark lost after a failed sync).

## Method

**What the spike implements.** It implements a `format.md` Part A append path and nothing more:
- Segments are preallocated to 64 MiB by writing zeros, then synced together with the directory. Each segment has
  the A.1 header. The next segment is created ahead, on another thread.
- A batch is facts blocks (A.5, every column plain: 24 payload bytes per reading) followed by one commit block
  (A.7). Every block and body is checked with CRC32C.
- One writer thread forms batches. With window 0 it takes the first queued reading and then whatever else is
  already queued, with no added delay. With window *w* it also takes whatever arrives within *w* of taking the
  first reading. A batch closes early at 1 MiB.
- A batch is written only after the previous batch's sync has returned. After the sync the mark is updated with
  three positional writes (`seq` odd, the fields, `seq` even), and only then is the batch acknowledged.
- The mark file is synced every second (§3 `mark_sync_interval`). The measurements use the writer thread, between
  batches and also when no batch comes; the mark table compares the other rules. The clean-shutdown sync is skipped
  once the writer is read-only, so a failed sync is never retried.
- The log directory is synced after the mark file is created.
- Not implemented: sealing (its cost is measured separately), entries blocks, other encodings and readers.

**Load.** The load is 100 series, each at *r* readings/s, staggered evenly, so arrivals are evenly spaced.
- The generator spins rather than sleeps, because a sleeping thread can wake late. How late it emitted against its
  schedule is reported (worst p99 of the three runs). Latency counts from the emit call, so a late generator does
  not add to it, but it does bunch arrivals, and it shows when other work held the CPUs.
- *Ack* latency runs from the emit call to the acknowledgement, after the sync and the mark update, and is stamped
  on the writer thread.
- *Delivered* runs to when a consumer thread receives the batch over a channel; that is the `design.md` budget. It
  was at most 0.09 ms above ack in any run.
- Back-pressure, which would hide latency from an open-loop load, is checked: the run fails if a paced run meets
  it, and none did.
- Each matrix cell and each mark rule ran three times, back to back. The brackets therefore show the spread
  within about a minute. A run made at another time can fall outside it: the previous full run did, at
  10,000 readings/s with no window. Runs at 100 readings/s last 20 s (2,000 samples, so p99.9
  there is the third-highest value), matrix runs at higher rates 8 s, mark runs 10 s. The segment-roll and
  call-comparison runs ran once (12 s and 8 s).
- Latencies inside one batch are not independent: every reading of a batch waits for the same sync. So p99.9 rests
  on the slowest few syncs of a run. That is why the tables give the spread across runs.

**Sync calls, fixed costs and device writes.** The sync-call table times each call after a 256-byte write, on an
otherwise idle store. Each call runs for 2 s or 20,000 syncs, whichever comes first; the `fsync` rows stop at the
cap.
- Device bytes come from macOS's cumulative block-storage write counter (`ioreg`), read before and after.
- The counter counts what the host sent to the device. Writes inside the SSD, its own write amplification, are not
  visible. So these figures are host writes, not NAND wear.
- The counter covers the whole machine, so the write-amplification rows subtract an idle baseline measured over the
  preceding 20 s (1,246 KiB/s in this run). They are approximate. The write-amplification runs synced the mark
  once a second on its own thread (about 10 mark syncs per row, included in the device bytes).
- `measure … calibrate` checks the counter: three times writing and syncing a 64 MiB file moved it by 64.2–64.3 MiB.

**Machine.** A 12-core ARM64 computer with 32 GiB of memory and its internal NVMe SSD, running macOS 27 with APFS.
The machine was in ordinary use, with other work running (load average 3.5–5). Builds ran at reduced priority. The
measurement runs, about 15 minutes in total, ran at normal priority so that the scheduler placed their threads like
any other. Linux and Windows were not measured: no such machine was available. Roadmap item 4.8 must measure them
on the target hardware.

**Reproduce.**

```text
cargo run --release -p commit --bin measure -- <dir> all         # about 13 minutes
cargo run --release -p commit --bin measure -- <dir> wa 20       # write amplification, about 1.5 minutes
cargo run --release -p commit --bin measure -- <dir> calibrate   # device counter check
cargo test -p commit                                             # failure behaviour and a real-file-system smoke test
```

The runs work in a `kvik-commit-measure` subdirectory of `<dir>` and remove it at the end.

### Failure behaviour, through the injectable file-system seam

The seam has two implementations: the real file system and a simulated one, which keeps a page cache apart from the
disk.
- A failed sync in the simulation follows Linux on ext4 and XFS: the dirty pages are marked clean without being
  written.
- Faults (`EIO`, `ENOSPC`) are injected on a write (optionally after a number of writes), a sync or a file
  creation. Free space is scripted. Syncs of chosen files can be held, and background writeback can be made to
  land after every write.
- Every row is a test in `spikes/commit/tests/faults.rs`.

| Injected | What the engine observes | Behaviour (spike follows §3) | Test |
|---|---|---|---|
| `EIO` on a log sync | The sync returns the error | Read-only, health fatal. The batch is not acknowledged and the mark is not advanced. Exactly one sync call, later emits refused. A restart on the same boot truncates to the mark (rule 1) | `a_sync_error_makes_the_writer_read_only_without_a_retry` |
| A second sync after the failure | Success, with nothing written | The reason a sync is never retried | `after_a_failed_sync_a_retried_sync_reports_success_without_writing` |
| Reboot after a failed sync whose bytes reached the disk | A complete batch beyond the mark | Kept, never acknowledged (row 12) | `after_a_reboot_a_batch_whose_sync_failed_may_be_kept` |
| Mark lost after a failed sync, same boot | A complete batch in the cache, none on disk | Rules 3 and 4 keep it and the sync "succeeds": a problem, Q-87 | `with_the_mark_lost_after_a_failed_sync_recovery_keeps_a_batch_that_is_not_on_disk` |
| `ENOSPC` on a log write | The write returns the error, before any sync | Read-only, fatal, nothing acknowledged | `no_space_on_a_log_write_is_fatal_and_nothing_is_acknowledged` |
| `ENOSPC` on a log sync | The sync returns the error | Read-only, fatal | `no_space_on_a_log_sync_is_fatal` |
| `ENOSPC` creating the next segment | The error, seen at the roll; a partial file left behind | Read-only, fatal, although every acknowledged batch is durable: a question, Q-86 | `no_space_when_preallocating_the_next_segment_is_fatal_although_nothing_is_lost` |
| `EIO` on the timed mark sync | The mark thread's sync returns the error | Read-only, fatal. No further mark sync, not even at shutdown | `a_failed_timed_mark_sync_makes_the_writer_read_only` |

The other tests cover:
- group commit (readings that arrive during a sync form the next batch);
- the mark covering exactly the acknowledged batches on disk;
- the timed mark on disk lagging until its sync;
- the writer-thread mark sync running when ingest stops;
- one clean-shutdown mark sync per rule, and the directory sync after the mark is created;
- the scanner: truncation at every byte of a batch, and a flipped byte anywhere in it.

`spikes/commit/tests/real_fs.rs` runs the real file system with every sync call the platform has. It creates a
preallocated segment, writes, syncs, checks free space and scans the result, and also commits through the writer.
In CI it is the only place the Linux `fdatasync` path runs.

## Which sync call the engine must use

- **macOS: `fcntl(F_FULLFSYNC)`.**
  - The `fsync(2)` manual page says that `fsync` moves data to the drive, but the drive may keep it in its cache
    and write it later and out of order. It adds that applications needing tighter guarantees should use
    `F_FULLFSYNC`.
  - `fcntl(2)` describes `F_FULLFSYNC` as asking the drive to flush all buffered data to permanent storage, and
    says it is implemented on APFS.
  - `F_BARRIERFSYNC` only orders writes: "no assumption should be made on what has been persisted or not when
    this call returns".
  - `fdatasync` is not documented on macOS.
  - The standard library's `sync_all` and `sync_data` already use `F_FULLFSYNC` there.
  - Directories are synced with the same call. Syncing a directory descriptor worked on APFS: it is part of the
    segment creation and seal timings.
- **Linux: `fdatasync`** for appends to a zero-filled preallocated segment; **`fsync`** after a length change (the
  seal's truncation) and on the directory after a create or rename.
  - The `fsync(2)` manual page (Linux man-pages) says that `fsync` includes flushing a disk cache if present.
  - The same page says that `fdatasync` skips metadata that is not needed to read the data back, such as the
    modification time but not the file size. Preallocation is what keeps the size unchanged.
  - The same page also says that a file's directory entry needs its own `fsync` on the directory.
  - Zero-filling matters on Linux. `fallocate` leaves unwritten extents, and their conversion on the first write
    is metadata that `fdatasync` must commit.
  - Not measured here.
- **Windows: `FlushFileBuffers`**, which the standard library calls for both `sync_all` and `sync_data`.
  Microsoft documents it as causing all buffered data to be written to the file. Whether it also flushes the
  device's cache must be checked with the device. Not measured here.

## Linux sync-error semantics, and what they mean for §3

Since 2018, Linux's behaviour after a failed writeback has been well documented: J. Corbet, "PostgreSQL's fsync()
surprise", LWN.net, 2018; A. Rebello et al., "Can Applications Recover from fsync Failures?", USENIX ATC 2020. On ext4
and XFS, when writeback of a dirty page fails, the error is reported to `fsync` (since 4.13, once to each open file
description), and the page is marked clean, not dirty. Btrfs behaves differently. It stays in the cache with the new bytes, which are not on disk. A
second `fsync` therefore returns success without writing anything, and reads keep returning the unwritten bytes
until the page is evicted. The error can come from writeback of any earlier write to the file, not only the last
one. `ENOSPC` and `EDQUOT` can likewise be reported at `fsync`, on file systems that allocate space at writeback.

For §3 this means:
1. **"Never retry on the same handle"** is right, but too narrow. A retry on any handle, in any process, can report
   success falsely. The rule should say that a failed sync is never retried, and that the file's contents since the
   last successful sync are unknown.
2. **Rule 1 is right.** After a failed sync, a restart on the same boot sees the failed batch complete in the page
   cache. Truncating to the mark is what keeps it out, so the mark must not advance past a failed sync. The spike
   shows both.
3. **Rules 3 and 4 have a gap (Q-87).** If the mark is missing on the same boot after a failed sync, the batch is
   kept. Rule 4's sync then succeeds without writing it, and it is delivered as durable.
4. **Copy-on-write file systems.** Preallocation does not protect against `ENOSPC` on Btrfs or ZFS, or on APFS when
   blocks are shared with a snapshot or clone. There `ENOSPC` can arrive at a write or at a sync. §3 treats both as
   fatal.

## Full disk

- The engine sees `ENOSPC` in one of three places:
  - when a segment is created and zero-filled, which on ext4 and XFS is where it lands, because later writes
    overwrite allocated blocks;
  - at a write, on a copy-on-write file system;
  - at a sync, on a file system that allocates at writeback.
- The critical mark (512 MiB) should normally stop ingest long before any of these. They then happen only if
  another process fills the disk between two free-space checks. A check costs 1–3 µs, so the engine can check
  before every batch and every segment creation.
- **Back-pressure works as §3 describes.** The writer stops taking from the queue, emits wait, and the wait is
  counted and timed. Nothing is dropped, and commits resume once space returns.
- **The low mark only degrades health.** The spike does no compaction, so it has nothing to pause.
- **Segment creation is the problem case.** It is the likeliest place for `ENOSPC`, and nothing is lost when it
  fails there. Yet §3 makes it fatal like a failed sync, and A.4 does not say what recovery does with the partial
  file (Q-86).

## Conclusions for `format.md` Part A and the log (roadmap 4.4, 4.5)

**Recommended for 4.4:**
- **Group-commit window: 0**, as in §3.
  - With an expensive sync the batch already grows with load, and the sync rate stays at about one per sync time
    (250–310/s here).
  - A 1 ms window saves about a third of the syncs at 1,000 readings/s. At 100 readings/s it saves nothing,
    because 100 staggered 1 Hz series arrive 10 ms apart, and it adds about 0.9 ms at p50.
  - `design.md` allows a window of a few milliseconds where it reduces write volume. A 5 ms window cut syncs by
    about 60 % from 1,000 readings/s up, at a p50 of about 8 ms (above the 5 ms figure) and a p99 of 13–14 ms. At
    100 staggered 1 Hz series it cut nothing. A 20 ms window put p99 at 24–28 ms, above the 20 ms figure.
  - Keep a byte cap. 1 MiB reached 7.2 million readings/s, far above any expected load.
- **Sync call:** `F_FULLFSYNC` on macOS, `fdatasync` on Linux (with `fsync` for metadata and directories),
  `FlushFileBuffers` on Windows. The choice belongs in one place, behind the file-system seam.
- **Next segment created ahead,** off the writer thread. Creating it at the roll stalls commits for 35–49 ms with
  64 MiB segments (this run and the previous one).
- **Seal off the writer thread.** A seal costs about 8–9 ms (truncate, sync, rename, directory sync), and the old
  segment receives no further batches.
- **Mark update by positional writes,** at 3–4 µs per update. Sync the mark between updates, on the writer thread,
  once a second, and also when no batch comes (the spike does this on the idle path, so the mark on disk lags by
  about one interval even when ingest stops). The commit-latency cost is within the run-to-run spread on either
  thread (see the mark sync table). The writer thread is preferred for two reasons:
  - on a separate thread the two `F_FULLFSYNC` calls wait for each other (mark sync about 9 ms against about 4 ms);
  - syncing between updates narrows, but does not close, the window in which a half-updated mark reaches the disk
    (problem 3 below).
- **Free-space check before each batch and each segment creation.**
- **Watch for interference.** `F_FULLFSYNC` drains the whole device queue. Compaction, tiering and other processes'
  writes lengthen the commit sync, so their bulk writes should not be synced while the log is busy, where that can
  be avoided.

**Recommended for 4.5:**
- Keep the seam's shape: write at an offset, sync, create preallocated, free space.
- Keep a simulated file system that models Linux's failed writeback, and its fault tests. Two limits of the
  spike's model:
  - It follows ext4 and XFS, as reported by Rebello et al. They report different behaviour for Btrfs, so 4.5
    should rely on neither the cache keeping nor the cache losing a failed batch.
  - It tracks dirtiness per file, not per page. A later write followed by a successful sync copies the whole cache,
    so it would "heal" a failed batch, which Linux would not do. The spike never syncs after a failure, but 4.5's
    harness should track pages.
- Settle Q-86 and Q-87.

**Budgets (`design.md`).**
- The budget (p50 ≤ 5 ms, p99 ≤ 20 ms) is set for Linux with an NVMe SSD, and macOS is not held to it.
- On this machine (macOS, not held to the budget), with the durable call and window 0: p50 3.9–5.8 ms and p99
  4.9–13.5 ms (medians of three runs). Against the Linux figures, p99 passes in every cell. p50 passes only at 100
  and 100,000 readings/s; at 1,000 and 10,000 readings/s every run was above 5 ms.
- The stretch goal of p50 ≤ 2 ms needs a sync well under 2 ms. Here the sync alone is about 4 ms.
- With plain `fsync`, p50 is 0.03 ms and p99 0.1 ms, but that is not durable on macOS.
- Whether the budget holds on Linux depends on how fast the device flushes its cache. 4.8 must measure that on the
  target hardware.

## Problems for Part A, §3 and the budgets

These are listed here, not redesigned.

1. **A.10's heading says the mark is "not synced".** §3 syncs it on a timer and at clean shutdown, and A.10's own
   fallback syncs it after every update.
2. **A.10 says the mark is "memory-mapped".** In Rust a memory map needs `unsafe`, for the writer and for a
   second-process reader. The workspace forbids `unsafe`, and a map also bypasses an injectable file seam.
   Positional writes cost 3–4 µs. A reader can keep the sequence lock with three positional reads (`seq`, the fields,
   `seq` again). Suggested wording: "updated in place".
3. **A half-updated mark (odd `seq`) can reach the disk.** A timed mark sync on another thread can run between the
   writer's three writes. So can the operating system's background writeback, whichever thread syncs
   (`writeback_between_the_mark_writes_can_put_a_half_updated_mark_on_disk`). After a power loss, rule 2's test
   ("below a valid mark … of any boot") then fails. Corruption below that mark is truncated as a torn tail and
   reported `possible_loss`, not recorded as a lost range with `data_lost`. Syncing between updates only narrows the
   window. Writing the whole mark with one positional write narrows it further, and a checksum in the mark would let
   recovery tell a torn mark from a valid one. The sequence lock alone cannot do either on disk.
4. **A.1 `base_sequence` is not known when a segment is created ahead of use.** The spike rewrites the header when
   the segment is taken into use, and the first batch's sync makes it durable. The format should say when the field
   is written.
5. **No per-OS sync call is named.** §13 says `fdatasync`, but on macOS that call is undocumented, and the
   manual pages name `F_FULLFSYNC` for durability. Part A or §3 should name the durable call per OS, as above.
6. **§13's remedy for sync rate and wear does not fit the workload.** Its remedy, a group-commit window of a few
   milliseconds (also in `design.md`), does nothing for 100 staggered 1 Hz series, which arrive 10 ms apart.
   On APFS the host wrote about 85–100 KiB per durable sync, about 0.75 TB a day for that load. A real reduction
   needs a window of 20 ms or more, which put p99 above the 20 ms figure, or readings batched before they reach
   the engine.
7. **A.10's fallback for a platform without a boot identifier is expensive.** Syncing the mark after every update
   halves the commit rate and puts p50 at 11.9 ms and p99 at 16.2 ms. Which platforms need it should be stated.
   Linux has `/proc/sys/kernel/random/boot_id` and macOS has `kern.bootsessionuuid`; no equivalent was found for
   Windows.
8. **§3 "never retry on the same handle"** should be "never retry", for the reason given above.
9. **Q-86:** a segment creation that fails with `ENOSPC` is both a write failure (fatal) and a full disk (wait).
   A.4 does not say what recovery does with a partial `.open` file.
10. **Q-87:** a mark lost on the same boot after a failed sync lets an unsynced batch be delivered.
