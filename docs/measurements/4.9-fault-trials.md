# 4.9 Fault trials on a hosted Linux runner

Gate 4.9, inputs for Q-52 (b) and Q-86 (b) (`model/OPEN-QUESTIONS.md`). The workflow is
[`fault-trials.yml`](../../.github/workflows/fault-trials.yml): it runs
[`scripts/trial-rewrite.sh`](../../scripts/trial-rewrite.sh) and [`scripts/trial-no-space.sh`](../../scripts/trial-no-space.sh)
as root on `ubuntu-latest`, driving the engine through [`log/examples/fault_trial.rs`](../../log/examples/fault_trial.rs)
on `StdFs`. The writer syncs the mark at every commit, and each start after a remount takes a new boot id, so that
rule 1's accepted loss on a same-boot remount with a timed mark does not count as a failure.

### No space on Btrfs (Q-86 (b))

A 512 MiB Btrfs loop device; 16 MiB segments; 1,000 readings per call; `disk_critical` 0, so the critical mark does
not make ingest wait before a write meets the full disk. After 50 acknowledged calls the file system was filled with
`dd` to 0 bytes free, then the writer resumed.

| | Copy-on-write (default) | `chattr +C` on the log directory before the first segment |
|---|---|---|
| What failed | the batch write into the zero-filled segment: `write` returned storage-full | nothing: batches went on into the zero-filled segment until it was full (833 calls), then the next segment's creation failed for lack of space and ingest waited (`DiskCritical`, Q-86 (a)) |
| Acknowledged after the fault | none (50 acknowledged, all before it) | not applicable (no fault) |
| (a) Remount with the disk still full | the start stays read-only (a write fails for lack of space); every acknowledged position reads back (by scan, as the reader cannot write its lease) | the start stays read-only (the manifest sync fails for lack of space); every acknowledged position reads back |
| (b) Fill removed | the start recovers, every acknowledged position reads back, a new batch commits | the same |

Reading: on Btrfs without copy-on-write turned off, zero-filling reserves nothing and lack of space surfaces at the
batch **write**, before any sync; it is a write failure on the log as settled at gate 3.3, nothing acknowledged is
lost, and a restart after space is freed recovers. With copy-on-write off for the log directory the reservation held
and no write failed; lack of space then took the path of Q-86 (a) (ingest waits). Only the write call was seen to
fail; a sync returning storage-full at a batch was not observed in this run.

### Rewrite on ext4 and XFS (Q-52 (b))

Every arm stopped before a verdict on the harness's own direct read of the device (`dd: IO error: Invalid input`),
after the engine's expected fault (for example a failed segment sync, `InputOutputError`, with nothing acknowledged
after it). A second run (43677554752), reading the loop device directly in its logical sector size (512 bytes there), failed the
same way. The script no longer uses direct reads: what reached the device is exactly what the loop driver wrote to
its image file, so it reads the image at the byte offsets the extents and the linear table give, without syncing or
flushing anything from outside. Before any verdict that reads the image, each arm checks that bytes synced long before
the fault (a file header's magic, or the probe's fill) are found at the computed offset, so an arithmetic error fails
the arm with a clear message. The third run passed (below).

## Third run (2026-11-15, run 43678199774): all jobs pass

The rewrite job with the image read and the mapping check, on the same runner image (kernel 7.0; e2fsprogs 1.47.2,
xfsprogs 6.18.0). All jobs passed: shellcheck, no-space (as in the first run), rewrite on ext4 and on XFS. In every
rewrite arm on both file systems the mapping check found the expected bytes at the computed offset first.

| Arm | ext4 | XFS | What it showed |
|---|---|---|---|
| probe | pass | pass | the sync over the failed sectors failed; **control**: a sync alone afterwards left the device without the new bytes, as the failed write-back had left the page clean; **treatment**: writing the same bytes again made the next sync write them |
| batch | pass | pass | the writer stopped at the failed segment sync (`InputOutputError`) with nothing acknowledged after it; with the mark removed, the start on the same boot wrote the last batch again and the device held it; every acknowledged position read back after a remount and a start under a new boot id |
| mark | pass | pass | the writer stopped at the failed mark sync; the start wrote the mark slot again and the device held it; every acknowledged position read back |
| manifest | pass | pass | with the manifest's sync failed while a start recorded a lost range, the next start wrote the record again and the device held it; the lost range survived the remount |

Reading: the control arm confirms on both file systems the kernel behaviour the in-place rewrite rules exist for
(Q-87, Q-117): after a failed write-back the page is clean, so a repeated sync does not write it. The treatment arm
and the engine arms confirm the remedy: identical bytes written again are written by the next sync. Q-52 (b) is
settled on Linux; macOS and Windows are not checked (owner decision pending on the wording).
