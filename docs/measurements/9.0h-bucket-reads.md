# 9.0h Bucket, window and calendar reads against the store's age

Roadmap item 9.0h: chart buckets, windows and calendar results fold a series' current facts in their range from the
sources (Q-1109) instead of building the reader's fact index. Measured with
[`kvik/tests/window_memory.rs`](../../kvik/tests/window_memory.rs):

```sh
KVIK_WINDOW_MEMORY_STEP=1 cargo test --release -p kvik --test window_memory -- --nocapture
```

## Method
- 37 series (gauges and counters in turn) on the in-memory file system, 16 MiB segments, one reading per series every
  step seconds of event time, which runs ahead of the clock (accelerated). The store is grown to 1, 7 and 30 days.
- At each age a fresh reader (64 MiB cap) refreshes, then reads: a bucket read over the last hour at one-minute
  steps (first, then again), a rolling one-hour window, and the calendar day the store ends in. Peak heap above the
  start of each read (`peak_alloc`), its time, and the heap the reader holds after them. Worst of a gauge and a
  counter.
- Before is the tree just before the change, with the same test file. Machine: a shared cloud virtual machine,
  four cores, 15 GB; other builds ran beside the 1 s after-run, so its times are indicative.

## Reading
- Before, the first such read builds the fact index (about 120 bytes a fact here) and the reader keeps it: memory
  and time grow with the store's age. After, every read is flat with age; what grows with the range read (a day at
  1 Hz, 86,400 facts) stays within the cap.
- The first read on a fresh reader takes about 16 MiB: the bytes of the segment its refresh follows and the lookups'
  cache (Q-1069), both bounded. Its time grows with the number of segments, whose indexes a lookup reads (Q-1109).
- A read again is slower than before (8 ms against 0.5 ms for an hour at 1 Hz; 0.2 s against 6 ms for a day): it
  reads the log each time, where before it answered from the index it held. Stored levels (7.1) and chunk reads
  (6.2) are what make repeated long reads cheap.

## Several series in one read, passes sized from counts (Q-1110, Q-1111)

The reads above are of one series. A dashboard reads every series over the same range, and every batch holds every
series, so one call per series decoded each batch once per series; a pass too large for its grant was read until it
filled, then halved and read again. Measured again after `buckets_of`, `window_of` and `facts_of` (one read for
several series), passes sized from the lookups' counts, and the rows folded as each pass is read.

### Method
- A store of 37 series (gauges, counters and states, each with its own delays of arrival), a reading a second each,
  built by one writer in 60-second slices of arrivals with event time accelerated: 1 day (3.3 million facts, 129 MiB
  on disk) and 7 days (23 million facts, 512 MiB), default configuration (64 MiB segments, 64 MiB reader cap), on
  disk, page cache warm, release build. The store is opened by its writer and read through its reader; each query
  runs twice on the same reader, first and again.
- Charts are `Resolution::Auto { max_points: 1_500 }` over the last 24 hours or 7 days of the store (a 1-day store
  has a day in its 7-day range); "an hour of buckets" is `Resolution::Step` of one minute over the last hour. Before
  and the index path take every series one call at a time; after takes them in one `buckets_of` or `facts_of` call.
- Before is 9.0h (`94c02a7`); the index path is the tree before 9.0h (`8cdf690`), whose first such read builds the
  whole store's fact index and whose later reads answer from it. Same machine, a shared cloud virtual machine with
  four cores; runs of the same query vary by up to 15%, and ranges give the runs seen.

### Reading
- All-series charts are within 2× of the index path at both ages (1.3–1.9×; the 7-day chart of the 7-day store
  1.6–2.0×), with no index and memory flat with age; before they were 30–75 times slower than it. A full
  read runs at 5–6 million facts a second.
- The 2× holds for all-series charts only. Against the index path, warm, per query:

  | Query | After against the index path |
  |---|---|
  | all series, 24 h | 1.4–1.9× |
  | all series, 7 d, 1-day store | 1.3–1.5× |
  | all series, 7 d, 7-day store | 1.6–2.05× |
  | one series, 24 h | about 8× |
  | one series, 7 d | 7.5–11× |
  | an hour of buckets | about 7× |
  | a rolling window (a tile) | about 10× (3.9 ms against 0.4 ms) |
  | a calendar day | about 17× (100 ms against 6 ms) |

  The index path's warm figures leave out building its index (8 s and 2.5 GiB at 7 days). Absolute times stay in
  milliseconds apart from charts. A dashboard gets the 2× only through `buckets_of` and `window_of`, one call for
  every series; tiles through `window` one series at a time cost about 10×.
- What is left is the decoding of every batch in range, since every batch holds every series (a one-series read
  decodes the other 36 series' rows too: 0.12 s for a day against the index path's 14 ms), and the exact arithmetic of
  the fold (about a fifth of a chart read, as on the index path). Layouts by series (6.2 chunk reads) and stored
  levels (7.1) are what make one series' long reads cheap.
- Not built: folding while the next pass is read, on a second thread (Q-1112; the fold is about two fifths of a long
  chart read); a hardware CRC32C (about 3%) and a span of event times per segment for a fresh reader's first read
  (Q-1111).
