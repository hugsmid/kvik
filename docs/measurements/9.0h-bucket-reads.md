# 9.0h Bucket, window and calendar reads against the store's age

Roadmap item 9.0h: chart buckets, windows and calendar results fold a series' current facts in their range from the
sources (Q-1109) instead of building the reader's fact index. Measured with
[`kvik/tests/window_memory.rs`](../../kvik/tests/window_memory.rs):

```sh
KVIK_WINDOW_MEMORY_STEP=1 cargo test --release -p kvik --test window_memory -- --nocapture
```

## Method
- 37 series (gauges and counters in turn) on the in-memory file system, 16 MiB segments, one reading per series every
  step seconds of event time, which runs ahead of the clock (accelerated). The store is grown to 1, 7 and 30 days.
- At each age a fresh reader (64 MiB cap) refreshes, then reads: a bucket read over the last hour at one-minute
  steps (first, then again), a rolling one-hour window, and the calendar day the store ends in. Peak heap above the
  start of each read (`peak_alloc`), its time, and the heap the reader holds after them. Worst of a gauge and a
  counter.
- Before is the tree just before the change, with the same test file. Machine: a shared cloud virtual machine,
  four cores, 15 GB; other builds ran beside the 1 s after-run, so its times are indicative.

## Reading
- Before, the first such read builds the fact index (about 120 bytes a fact here) and the reader keeps it: memory
  and time grow with the store's age. After, every read is flat with age; what grows with the range read (a day at
  1 Hz, 86,400 facts) stays within the cap.
- The first read on a fresh reader takes about 16 MiB: the bytes of the segment its refresh follows and the lookups'
  cache (Q-1069), both bounded. Its time grows with the number of segments, whose indexes a lookup reads (Q-1109).
- A read again is slower than before (8 ms against 0.5 ms for an hour at 1 Hz; 0.2 s against 6 ms for a day): it
  reads the log each time, where before it answered from the index it held. Stored levels (7.1) and chunk reads
  (6.2) are what make repeated long reads cheap.
